# 内容分布式显示系统 —— 架构设计与硬件选型

> 版本：v0.1（设计阶段，未含代码）
> 日期：2026-07-13

## 1. 背景与目标

- 客户在**微信小程序**中上传介绍自己公司的图片/视频；
- **运营方**审核确认内容无误后，将内容发布到该客户**专属的显示屏**（LCD 1920×1080）上循环播放；
- 显示屏数量为**小批量**，与运营方服务器同处一个场地局域网；
- 设计目标：低成本、可离线（外网中断不影响播放与分发）、无人值守可靠运行（防假死）。

## 2. 总体架构

服务端、媒体存储、转码**全部部署在运营方本地服务器**上，与显示屏同在场地局域网。
微信小程序经公网入口访问本地服务端；显示屏走局域网下载。
**外网中断只影响客户上传新内容，不影响已审核内容的分发与播放。**

```
                    公网                          场地局域网
微信小程序(客户) ──HTTPS──> ┌─────────运营方本地服务器─────────┐
   · 上传图片/视频          │  服务端 API                      │
   · 查看审核状态           │   · 审核工作流 / 内容状态机       │ <──轮询 manifest── 显示屏 1
                           │   · 设备管理 / manifest 生成      │ <──心跳上报──────  显示屏 2
运营方管理后台(Web) ──────> │  FFmpeg 本地转码                 │ ──媒体文件下载──>   ...
   · 审核 / 绑定 / 编排     │  媒体存储(本地磁盘 + Nginx 静态)  │                    显示屏 N
   · 设备监控 / 告警        │  元数据库(MySQL/SQLite)          │
                           └─────────────────────────────────┘
```

### 2.1 组成部分与职责

| 组件 | 职责 |
|---|---|
| 微信小程序（客户端） | 微信登录；上传图片/视频；提交审核；查看审核状态与驳回原因 |
| 运营方管理后台（Web，局域网访问） | 审核队列（通过/驳回+原因）；**内容与客户/显示屏的绑定由运营方指定**（客户不参与绑定）；播放列表编排；设备监控（在线/版本/告警） |
| 服务端（RESTful API） | 内容状态机；设备管理（注册/绑定/心跳）；按设备生成带版本号的播放清单 manifest；调用本地 FFmpeg 转码 |
| 存储与转码（本地） | 媒体文件存本地磁盘，由 Nginx 静态分发（可选 MinIO）；FFmpeg 统一转码；元数据 MySQL/SQLite；定期备份（可选云端异地备份） |
| 显示屏设备（边缘端） | 局域网轮询 → 下载缓存 → 循环播放；多级看门狗；状态上报 |

### 2.2 前置条件：小程序公网入口

微信小程序的网络请求要求服务端具备**已备案的 HTTPS 域名**。本地化部署下需要：

- 固定公网 IP + 端口映射，或 frp/nps 等内网穿透到一台有公网 IP 的跳板；
- 一个已 ICP 备案的域名 + HTTPS 证书（Let's Encrypt 即可）；
- 在小程序后台配置该域名为"request/uploadFile 合法域名"。

这是整个系统**唯一依赖外网**的环节。

## 3. 内容生命周期（状态机）

```
客户上传 ──> 待转码 ──FFmpeg──> 待审核 ──运营方通过──> 已通过 ──绑定/编排──> 已发布(进入设备manifest)
                                  │
                                  └──运营方驳回(附原因)──> 已驳回(客户可见原因，可重新上传)
```

- **统一转码**是关键环节：所有上传视频经 FFmpeg 转码为 **H.264 High Profile / 1080p / MP4（faststart）**，图片统一转为 1920×1080 JPEG/PNG。这保证了低价 SoC 上硬解码 100% 可用，避免客户上传的奇异编码（H.265 10bit、VP9、竖屏 4K 等）在端侧播不动或花屏。
- 转码完成后计算 sha256 与文件大小，写入元数据，供端侧校验。

## 4. 分发协议（轮询方案细化）

保留"设备轮询"的原设想（实现简单、故障模式清晰、无长连接状态要维护），用 HTTP 条件请求把轮询成本降到极低：

### 4.1 拉取播放清单

```
GET /api/v1/device/manifest
Headers:
  X-Device-Id:   <设备ID>
  X-Device-Sign: <HMAC(device_secret, timestamp + path)>
  If-None-Match: "<当前已应用的manifest版本号>"
```

- 无更新 → `304 Not Modified`（响应体为空，开销极小，轮询间隔可设 30s~2min）；
- 有更新 → `200` + JSON：

```json
{
  "version": "20260713T102030-8f3a",
  "items": [
    {
      "id": "c_1001",
      "type": "video",
      "url": "/media/c_1001_1080p.mp4",
      "sha256": "…",
      "size": 10485760,
      "duration": 30,
      "order": 1,
      "valid_from": null,
      "valid_to": null
    },
    {
      "id": "c_1002",
      "type": "image",
      "url": "/media/c_1002.jpg",
      "sha256": "…",
      "size": 512000,
      "duration": 10,
      "order": 2
    }
  ],
  "commands": []
}
```

- `url` 为相对路径，媒体由 Nginx 直接静态分发——**API 进程不经手大文件**；
- `commands` 为可选运维指令通道：`reboot`、`upload_logs`、`ota`、`screenshot` 等，随轮询顺带下发，无需额外长连接。

### 4.2 设备端更新流程

1. 收到新 manifest → 对比本地缓存，只下载缺失/变更的文件；
2. 下载支持**断点续传**（HTTP Range），完成后校验 **sha256**；
3. 所有条目就绪后**原子切换**播放列表（播完当前项再切，画面无中断）；
4. 删除不再被任何 manifest 引用的旧文件；
5. 任一环节失败 → 保持旧列表继续播放，指数退避重试。

**断网兜底**：设备始终播放本地已缓存内容；网络恢复后自动追平最新版本。

### 4.3 心跳与监控

```
POST /api/v1/device/heartbeat
Body: { "version": "…", "uptime": 86400, "disk_free_mb": 2048,
        "temp_c": 52, "playing": "c_1001", "player_ver": "1.0.3" }
```

- 服务端记录最近心跳时间，超时（如 5 分钟）标记设备离线并向运营方**告警**（管理后台红点 + 可选微信/短信通知）；
- 心跳频率 1 分钟一次，与 manifest 轮询可合并为同一次请求以进一步简化。

## 5. 设备端可靠性设计（多级看门狗）

单靠应用层 watchdog 不足以覆盖所有假死场景，采用四层递进：

| 层级 | 机制 | 覆盖的故障 |
|---|---|---|
| 1. 硬件看门狗 | SoC 内置 watchdog（`/dev/watchdog`，晶晨/全志/瑞芯微均支持），由喂狗守护进程喂狗 | 内核 panic、系统整体假死 → 硬复位 |
| 2. 进程守护 | systemd `Restart=always` + `WatchdogSec`（播放器需周期性 `sd_notify`） | 播放器崩溃、进程假死 |
| 3. 应用自检 | 播放器周期写心跳文件/上报播放进度；守护脚本检测"进度长时间不前进"则重启播放器 | 播放卡死但进程未死（如解码器挂起） |
| 4. 定时重启 | 每日凌晨业务空窗期定时重启（cron/systemd timer） | 内存泄漏、资源慢性耗尽等一切慢性病（保底） |

其他可靠性措施：

- **只读根文件系统**（overlayfs），媒体缓存放独立可写分区——断电不会损坏系统盘；
- 二手盒子方案自带 **eMMC**，天然比 SD 卡抗掉盘；开发板方案建议用工业级 SD 卡或 eMMC 模块；
- 设备预置 `device_id + device_secret`（烧录镜像时写入或首次启动生成后在后台登记）；设备与客户的绑定关系由运营方在管理后台维护；
- 播放器/代理程序支持 **OTA**：manifest 的 `commands` 下发新版本 URL + 校验和，A/B 双版本目录切换，失败自动回滚。

## 6. 对原设想的改进点汇总

| 原设想 | 改进 | 理由 |
|---|---|---|
| 设备轮询 server | **保留**，加 `If-None-Match`/304 条件请求 | 轮询成本降到近零，30s 级轮询也无压力；比 MQTT 少一套要运维的组件。量大或需秒级推送时再引入 MQTT 不迟 |
| 服务端接收/下发内容 | API 只发 manifest（元数据），媒体由 Nginx 静态分发 | 大文件不过 API 进程，简单且高效 |
| （未提及） | 增加**统一转码**环节 | 低价 SoC 硬解稳定性的成败关键 |
| 端侧 watchdog | 扩展为**四级看门狗** | 单层 watchdog 覆盖不了内核假死/慢性泄漏 |
| （未提及） | 心跳 + 离线告警 + 远程指令 + OTA | 屏挂在客户面前，运营方必须先于客户发现故障 |
| 云端存储（常见做法） | **本地化部署** | 按需求：外网中断不影响分发与播放；小批量下也省了云成本 |

## 7. 嵌入式硬件选型

### 7.1 需求与约束

- 1080p HDMI 输出（LCD 1920×1080 + HDMI 驱动板）；
- 以太网：**百兆即可**（1080p H.264 码率 ~8Mbps，且是下载缓存不是实时流）；
- **不需要 PoE**：液晶面板本身需要独立供电，PoE 省不掉电源线；
- H.264 1080p 硬解码；能跑 Linux（Armbian）；
- 小批量采购。

### 7.2 候选方案对比

| 方案 | 参考价（整机/板卡） | 优点 | 风险/缺点 |
|---|---|---|---|
| **二手运营商电视盒子**（晶晨 S905L3/S905L3A：魔百盒 M401A、UNT403A 等，闲鱼） | **¥25–50 整机** | 绝对最便宜；自带外壳+电源+遥控+**eMMC**+百兆网+HDMI；ophub Armbian 支持成熟 | 无保修；货源批次不一；需逐台刷机验机；部分批次锁 bootloader |
| 全新白牌盒子（X96Q 类，全志 H313） | ¥60–90 整机 | 全新；同样自带壳/电源/eMMC | 存在以次充好（标 H313 实为 RK3229），需验机 |
| Orange Pi One（全志 H3，1GB，百兆网，HDMI） | ~¥70–90 板卡 | 全新有保修的最低价开发板；Armbian 主线支持多年 | 需另配电源/SD 卡/外壳（+¥30–50），总价与 Zero 3 接近 |
| **Orange Pi Zero 3 1GB**（全志 H618） | ¥99 板卡 | 在售新品、DDR4、软件支持活跃；稳妥基准 | 同样需配电源/SD 卡/外壳；千兆网口用不上（白送） |
| 广告机一体主板（RK3566/A133，LVDS/eDP 直驱屏） | ¥150–250 | 省掉 HDMI 驱动板；自带看门狗/RTC/定时开关机；行业成熟 | 单价高，适合后期量产再评估 |

### 7.3 推荐结论（小批量）

- **验证期 / 能接受刷机折腾**：二手 **S905L3A 运营商盒子**（¥30–50 整机含壳含电源），单台综合成本最低，eMMC 启动比 SD 卡更可靠。建议一次购入**同批次同型号**并预留 20% 备机。
- **要全新保修、省事**：**Orange Pi Zero 3 1GB（¥99）**，软件生态最新；Orange Pi One（~¥80）差价很小，默认推荐 Zero 3。
- 成本视角提醒：主板低于 ¥60 后已不是成本大头——电源、工业级 SD 卡、外壳、**一次现场维护的人工成本**都超过省下的差价。"更贵但更稳"在总拥有成本上往往更便宜。
- **软件路线统一**：Armbian/Debian + mpv（硬解）+ 自研轻量代理（下载/轮询/看门狗/心跳）。全部候选硬件共用同一套软件栈，后期换硬件**不用改代码**。
- 若后期量产，可评估**广告机一体主板直驱 LCD（LVDS/eDP）**，去掉"HDMI 驱动板"一层，整机 BOM 与故障点都更少。

## 8. 附：二手 S905L3A 盒子刷 Armbian 指南

以最常见的中国移动魔百盒 **M401A / UNT403A**（S905L3A）为例，使用 ophub 的
[amlogic-s9xxx-armbian](https://github.com/ophub/amlogic-s9xxx-armbian) 固件。

1. **选购**
   - 闲鱼按型号采购**同批次**（M401A 最经典、资料最全）；
   - 也可直接买标明"已刷 Armbian / 已开启 U 盘启动"的成品，溢价约 ¥10–20，省去逐台折腾。
2. **下载镜像**
   - 在 ophub Releases 中选择 `s905l3a` 对应镜像（形如 `Armbian_..._amlogic_s905l3a_*.img.gz`）。
3. **写 U 盘**
   - 用 balenaEtcher / Rufus 将镜像写入 U 盘；
   - 编辑 U 盘 `/boot/uEnv.txt`，将 `FDT` 行指向对应 dtb（如 `meson-g12a-s905l3a-m401a.dtb`）。
4. **U 盘启动**
   - 盒子断电、插入 U 盘；
   - 牙签按住盒内 reset 键（部分型号藏在 AV 孔内）同时上电，保持约 5 秒；
   - 成功后从 U 盘引导进入 Armbian（默认账号 `root` / `1234`）。
5. **写入 eMMC**
   - 在 U 盘系统内运行 `armbian-install`，选择对应机型/dtb；
   - 完成后关机、拔 U 盘、重新上电，即从 eMMC 运行。
6. **避坑与验机**
   - 部分新批次盒子**锁了 bootloader**（如某些 E900V22C），需拆机短接用 USB Burning Tool 线刷解锁底包——采购时避开，认准 M401A/UNT403A 等易刷型号；
   - 每台刷完跑一遍验机清单：CPU 型号（`cat /proc/cpuinfo`）、内存容量、HDMI 1080p 输出、网口连通性、mpv 硬解播放测试片。

## 9. 建议的技术栈与后续里程碑

**技术栈建议**（实现阶段可再议）：

- 服务端：Go（单二进制、部署简单）或 Node.js/Java；Nginx 反代 + 静态媒体分发；MySQL（或起步用 SQLite）；FFmpeg 转码队列；
- 管理后台：任意主流前端框架（Vue/React），局域网访问；
- 小程序：微信原生框架，`wx.uploadFile` 分片上传大视频；
- 设备端：Armbian + mpv（IPC 控制）+ Go/Python 轻量代理（轮询、下载、看门狗喂狗、心跳、OTA）。

**里程碑**：

1. M1 端到端打通：服务端 manifest/心跳 API + 1 台盒子播放器代理，人工放文件即可播；
2. M2 管理后台：审核工作流 + 设备绑定 + FFmpeg 自动转码；
3. M3 小程序：上传 + 审核状态查询（含公网入口与域名备案）；
4. M4 可靠性收尾：四级看门狗、只读根文件系统、OTA、离线告警、验机/产线刷机脚本。
