# 内容分布式显示系统 —— 架构设计

> 硬件：**Orange Pi One**（全志 H3，选型见 [hardware.md](hardware.md)）+ LCD 1440×900。
> 本文讲**为什么这么设计**；怎么装、怎么用见 [deployment.md](deployment.md)。

## 1. 目标

运营方把各客户的宣传图片、视频、PDF 下发到客户**专属的显示屏**上循环播放，屏上同时显示房间号等属性。
显示屏小批量、与运营方服务器同处一个场地局域网。设计目标：

- **低成本**：几十元级的开发板，服务端一台普通机器；
- **可离线**：安装完成后只依赖局域网，外网中断不影响分发与播放；
- **无人值守**：设备装好后很难再物理接触，除首次装机外的一切变更都要能远程完成，故障能自愈。

客户自助上传（微信小程序）与审核流程尚未实现，见第 7 节"规划"。

## 2. 总体架构

```
运营方浏览器 ──HTTPS :9001──> ┌──────── display-server（运营方本地服务器，Go 单进程）────────┐
  管理后台（内嵌单页）          │  管理 API / 设备 API / 文件分发（Range）                      │
                              │  模板渲染（纯 Go）  视频转码（ffmpeg）  PDF 逐页渲染（poppler）│
新设备 ──HTTP :9000──────────> │  状态：data/state.json  内容：data/media/<设备>/               │
  只有一键装机脚本与程序包       └────────────────────────────────────────────────────────────┘
                                   ▲ 轮询清单（ETag/304）  心跳  下载文件  ── HTTPS :9001，指纹固定 + HMAC 签名
                                   │
                    显示屏 1…N：Armbian + display-agent（Go）+ gstplayer.py（GStreamer，DRM 直出）
```

| 组件 | 职责 |
|---|---|
| 管理后台（`internal/web`） | 设备列表与健康状态、每台设备的属性/模板/播放列表、测试屏、模板与时段、程序包上传与下发、文件缓存区配额 |
| 服务端（`internal/server`） | 设备自注册与认证；按设备生成带版本号的清单；上传处理（转码、缩图、PDF 渲染）；文件分发；程序包 OTA 下发 |
| 状态（`internal/store`） | 一个 JSON 文件（原子写入），规模小不值得引数据库；媒体文件就是目录里的文件 |
| 设备代理（`internal/agent`） | 自注册、轮询、断点续传下载与校验、原子切换、心跳、整包 OTA、时钟校准、现场救援控制台 |
| 播放进程（`internal/player`） | Python + GStreamer，cedrus 硬解，两个 DRM 硬件图层叠出模板与媒体；代理守护它 |

## 3. 分发协议

设备轮询（实现简单、故障模式清晰、没有长连接状态要维护），用 HTTP 条件请求把轮询成本降到近零。
报文类型定义在 `internal/manifest/protocol.go`，两端共用。

### 3.1 拉取播放清单

```
GET /api/v1/device/manifest
Headers:
  X-Device-Id:   <设备ID>
  X-Timestamp:   <unix 秒>
  X-Device-Sign: <HMAC-SHA256(device_secret, timestamp + method + path)>
  If-None-Match: "<当前已应用的清单版本号>"
```

无变化回 `304`（空响应体）；有变化回 `200` + JSON：

```json
{
  "version": "3f9c1a2b7d04",
  "items": [
    { "type": "video", "name": "promo.mp4", "url": "/media/scr-0017/promo.mp4",
      "sha256": "…", "size": 1937024, "duration": 0 },
    { "type": "image", "name": "menu.jpg", "url": "/media/scr-0017/menu.jpg",
      "sha256": "…", "size": 186000, "duration": 10 }
  ],
  "layout": {
    "canvas_w": 1440, "canvas_h": 900,
    "media": { "x": 720, "y": 0, "w": 720, "h": 900 },
    "overlay": { "type": "image", "name": "ovl_a1a2b9def825.png",
                 "url": "/render/scr-0017/ovl_a1a2b9def825.png", "sha256": "…", "size": 6046, "duration": 0 }
  },
  "update": { "version": "v1.3.0", "url": "/packages/display-agent-v1.3.0-armv7.tar.gz", "sha256": "…", "size": 5242880 }
}
```

- `version` 是条目、叠加布局、待执行更新的哈希：任何一项变了就变，内容不变则稳定；
- `items` 按顺序循环播放；`duration` 只对图片有效（来自模板），视频播完即切；
- `layout` 只在模板有媒体区且媒体区有内容时出现（见 4.2）；没有时 `items` 是一张整屏渲染图；
- `update` 只在这台设备有待执行的程序更新时出现（见第 5 节）；
- 文件（`/media/`、`/render/`、`/packages/`）由同一个服务进程分发，支持 Range 断点续传，同样要求设备签名、
  且只能取自己目录下的文件。几十台设备的规模下不值得再引一个 Nginx。

**服务端开销**：清单的全部输入汇总成每台设备一份 `content`（一次读锁取齐状态与文件元数据，不渲染），
清单按它的指纹缓存——指纹不变就直接复用，10 秒一次的轮询不会反复渲染 PNG、哈希文件、列目录。

### 3.2 设备端更新流程

1. 收到新清单 → 只下载本地缺失的文件（文件名带 sha256 前缀，内容相同即复用）；
2. 下载支持断点续传，边下边算 sha256，校验通过才改名；
3. 全部就绪后原子切换播放列表，并写入 `current.json`（断网重启时据此恢复）；
4. 删除不再被引用的旧文件；
5. 任一环节失败 → 继续播放旧列表，指数退避重试（上限 5 分钟）。

### 3.3 心跳与在线判断

```
POST /api/v1/device/heartbeat
Body: { "agent_version": "v1.3.0", "uptime": 86400, "disk_free_mb": 2048, "temp_c": 52,
        "hwdec": "v4l2slh264dec", "output_w": 1440, "output_h": 900, "update_error": "" }
```

- **在线判断不靠心跳**：设备的任何签名请求（轮询、心跳、下载）都算联系过，约 3 个轮询周期（至少 30 秒）
  没有请求即判离线。下载也要算，因为下载大文件时轮询会暂停；
- **间隔由服务端规定**（`server.json` 的 `poll_interval_s` / `heartbeat_interval_s`），随每个响应头
  `X-Poll-Interval` / `X-Heartbeat-Interval` 下发，设备照办；
- 心跳只做健康上报（温度、实际解码器、输出分辨率、运行时长、剩余空间、程序更新失败原因）与 OTA 确认；
  设备 IP 由服务端从连接上取，正在显示的版本由轮询的 `If-None-Match` 带来，都不在心跳里。

## 4. 管理后台、模板与内容

### 4.1 管理后台与同步状态

服务端内嵌单页管理后台（`GET /admin`，`X-Admin-Token` 认证；口令必须配置，否则服务端不启动），
桌面与 iPhone/iPad 触屏同一套页面：

- 设备列表：在线状态（离线显示最后在线时间）、IP、版本、硬解/温度/输出分辨率，以及内容同步状态；
- 每台设备：测试屏（1/5/15 分钟）、key-value 属性（如 `room=302`）、内容（模板 / 左右对调 / 播放列表：
  逐个上传带进度，上传与转码中即可拖动排序，顺序自动保存）；
- 模板与时段、程序更新、存储（文件缓存区配额）。

**同步状态怎么来的**：后台看的就是 3.1 里清单缓存用的那份 `content` 指纹。设备每次轮询时记下"当时的指纹、
算出的版本、设备带来的 `If-None-Match`"。后台刷新时重算指纹：和上次不同 → 等待刷新（该显示的内容变了，
设备还没来取）；设备显示的版本 ≠ 应显示的版本 → 正在刷新；一致 → 已显示最新内容。
只看这台设备自己的输入；时段到点切换、测试屏到期这类没有写入的变化也能体现；不需要设备额外上报。

### 4.2 模板在服务端渲染成图

模板是画布 + 区域列表：

| 区域类型 | 内容 | 谁来画 |
|---|---|---|
| `attribute` | 设备属性值（按 key 取，如 `room`） | 服务端 |
| `text` | 固定文字 | 服务端 |
| `media` | 该设备的播放列表：图片/视频/PDF | **设备端**（每个模板至多一个） |

服务端把模板合成为一张 1440×900 PNG（纯 Go，`golang.org/x/image`），按媒体区里有没有内容分两种：

- **整屏图**（没有媒体区，或媒体区还没放内容）——作为普通图片条目走既有管线，也是"刚建好还没传内容"时不黑屏的兜底；
- **叠加图 + 设备端播放**（媒体区有内容）——媒体区挖成全透明，清单条目就是媒体文件本身，叠加图随 `layout` 下发。

设备端由 GStreamer 出画面（`internal/player/gstplayer.py`，编译进代理、启动时写到 `cache_dir`，由代理守护），
**不经 GPU、不做软件合成**，直接用显示控制器（Allwinner DE2）的两个硬件图层叠出整屏：

| 图层 | 内容 | 怎么来 |
|---|---|---|
| 上层（主图层，ARGB） | 模板叠加图，媒体区是全透明的"洞" | 播放进程经 libdrm 直接驱动：自己设显示模式，两块哑缓冲轮换，画好后台那块用 `drmModeSetPlane` 切过去 |
| 下层（VI 图层，NV12，硬件缩放） | 当前播放项，按 cover 撑满媒体区 | 每项一条管线，输出交给只管这一个图层的 `kmssink`。视频走 `v4l2slh264dec`（cedrus 硬解），NV12 dmabuf 零拷贝显示，`videocrop` 只打裁剪标记、`kmssink` 按标记取源矩形；图片在软件里裁剪、缩放成正好媒体区大小，1:1 显示 |

上层不用第二个 `kmssink`，是因为两个 `kmssink` 共用一个 DRM fd（只能有一个 DRM master）时会互相
干扰：各自等翻页/vblank 事件会抢走对方的事件，非阻塞翻页还会撞上另一边进行中的提交（EBUSY），
表现为画面卡住不动、也不报错。现在两个图层的提交都是阻塞式的，谁都不向 DRM 要事件。图层 id 由播放进程
经 libdrm 查出（主图层在上，第一个能显示 NV12 的覆盖图层在下），上下顺序用 `zpos` 显式指定。
这与 Kodi/LibreELEC 在 Allwinner 主线内核上的做法一致。

视频不走 `playbin` 的自动连接，而是写死成 `filesrc ! qtdemux ! h264parse ! v4l2slh264dec ! capsfilter ! videocrop ! kmssink`
（服务端已把视频统一转成 MP4/H.264）。原因在格式协商：解码器第一次协商时 `playbin` 还没把它连到输出上，
由 `playbin` 代答"下游吃什么"，并把解码器自己能出的全部格式附在答案末尾；`v4l2slh264dec` 再按自己的偏好排序，
选中 Allwinner 分块格式 NV12_32L32，下游显示不了，只能退到逐帧软件解分块（卡顿）。写死之后解码器从一开始
就连着 capsfilter，只能在**线性格式的系统内存 caps**（`video/x-raw,format={NV12,I420}`）里选：放开内存类型会协商成
DMA_DRM caps，而这条路上的分配查询拿不到 VideoMeta，解码器判协商失败。帧仍是解码器的 dmabuf，`kmssink` 直接导入，不拷贝。

**绕开 cedrus 首帧解坏**：实测每个解码会话解的第一帧只解出顶上一截，其余是没写过的缓冲（显示成绿色），
后面的帧都参考它，绿斑要到下一个 I 帧才消失。所以写死的管线会把第一帧码流复制一份先送进解码器当牺牲品，
它解出来的那一帧在解码器出口丢掉，输出的帧数与时间戳不变。

每个视频文件按 `裁剪撑满 → 不裁（留黑边）→ playbin 自动连接 + 软件转格式后再裁` 的顺序尝试，记住它第一个放得起来的
方式；最后一种什么封装、编码都能放（如直接拷进目录、没转码的文件）。每次退一步都在日志里写明原因，
每项第一次显示时记下解码器与输出方式。GStreamer 自身的错误和 `kmssink`、`v4l2codecs` 的警告也转进日志。

叠加图按**显示屏实际输出分辨率**光栅化成预乘 alpha 的 BGRA（`<png>.1920x1080.bgra`），媒体区按同一比例换算：
显示屏若按 1920×1080 输出而模板是 1440×900，画面整体等比放大，不会错位。输出分辨率由 `agent.json` 的
`display_mode`（`宽x高`）决定，显示屏不提供时退回首选模式。

**切换过渡**：约 0.6 秒"淡出到黑 → 淡入"，做在上层：往洞里填透明度渐变的黑色、逐帧切给主图层，每一步只重画洞所在的行。
下层的硬解视频帧是 dmabuf，CPU 碰不得；切换空档里洞是全黑的，拆旧管线、建新管线的那一下看不出来。

属性文字变化只重发叠加图，视频原封不动。播放进程退出，或每 10 秒一次的状态查询（同时取回当前解码器）不回，
代理就重启它并重新下发当前画面。

> 本地用真实 GStreamer 验证了排期、坏文件跳过、解码器上报、cover 裁剪计算与图片裁剪缩放
> （fakesink 代替 kmssink、软解代替 cedrus），上层画面的拼法有单测。**DRM 图层叠加（zpos 与透明洞）、cedrus 硬解与 dmabuf
> 零拷贝必须在样机上确认**，再对整批设备下发。

其他规则：

- **清单优先级**：测试屏（未过期）> 设备专属模板 > 时段命中 > 全局默认模板；测试屏到期自动回落，无需清理任务。
  首启播种一个左右分屏模板并设为全局默认，最后一个模板不可删，所以不存在"没有模板"的分支；
- **时段计划**：全局的 `{模板, 星期, 开始, 结束}` 列表，取第一条命中，支持跨午夜。服务端按 `timezone` 在生成清单时解析，
  到点渲染图变化 → 版本变化 → 设备下一次轮询切换，设备端不需要可信时钟；
- **播放顺序只有一个来源**：后台写入的顺序，加上直接拷进 `media_root/<设备>/` 但没记录过的文件（按名字排在后面）。
  后台列表与设备清单用同一个函数计算；
- **左右对调**：每台设备一个 `mirror` 开关，渲染时把每个区域的 x 换成 `W-(x+w)`（文字不镜像），一个模板两种摆法；
- **底图**：节日主题等区域画不出来的画面，模板可以垫一张底图（`data_dir/backgrounds/`，按内容命名，换图即换名，
  清单缓存键自然跟着变）。按画布等比铺满、居中裁切，解码缩放结果在渲染器里缓存；区域不设底色时透明、透出底图；
  媒体区照旧挖洞，所以底图的这块要留空。底图里一般有文字，不能水平翻转，所以对调的设备用另传的对调版
  （没有对调版时用原图，后台提示）。后台给设计师下载参考图：画布原尺寸，媒体区标红写明坐标，各区域标框。
  底图合进叠加图，设备端不用改；
- 文字渲染需要 CJK 字体（`font_path`），未配置时退回内嵌拉丁字体，中文显示为方框。

### 4.3 上传处理

上传时在服务端处理一次，所有设备都省事。处理在后台串行执行，产物先写成隐藏文件、完成后改名，
未完成前不会出现在清单里。上传限制随 `/api/v1/admin/info` 下发给后台页面，只在服务端定义一处。

- **视频**一律转码（`internal/transcode`，调用 ffmpeg）：H.264 High@4.0、x264 `fastdecode`（关掉 CABAC 与环路滤波，
  解码 CPU 省三四成）、等比缩到 1440×900 以内（只缩不放）、≤ 30fps、CRF 22（码率随内容走，封顶 4Mbps）、去音轨、faststart。
  不用固定码率：那会把简单素材也撑到目标码率。最初设想运营方素材可控、只校验即可，现场证明不行——即使是 H.264，
  原片 10~20Mbps 的码率也会让 H3 持续发热、降频乃至过热关机。所以**没有 ffmpeg 时不收视频**，后台醒目提示。
- 为什么仍是 H.264：H3 的 cedrus 是无状态解码器，要 V4L2 Request API，FFmpeg 上游没有这部分支持（所以 mpv 只能软解，
  这是改用 GStreamer 的原因），GStreamer 的 v4l2codecs 原生支持；H3 上 H.264 硬解比 H.265 成熟、不支持 10-bit HEVC，
  局域网分发省那点体积意义不大，编码 H.265 还要慢 5~10 倍。`fastdecode` 是给硬解失效时兜底的：退化成软解也还放得动。
- **图片**纯 Go 等比缩到 1440×900 以内：设备只有 1GB 内存，解码后的位图是 宽×高×4 字节。
- **PDF** 用 poppler-utils 逐页渲染成 1440 宽的 JPEG（`pdfinfo` 取页数、识别加密，`pdftoppm` 逐页渲染以便报进度、可取消），
  放在 `media_root/<设备>/.pages/<文档名>/`，全部完成后原 PDF 才出现在播放列表。播放列表里一个 PDF 是一项，
  生成清单时展开成逐页的图片条目，设备端看到的就是普通图片。

ffmpeg 与 pdftoppm 只在服务端启动时查找一次，装好后重启服务端生效。

### 4.4 文件缓存区（上传去重、按最久未使用淘汰）

处理好的内容在 `media_root/.store/` 各存一份，以内容 sha256 命名（PDF 另有 `<sha>.pages/`）；设备目录里的文件是指向它的
硬链接（不支持硬链接的文件系统退回复制）。索引 `data_dir/cache.json` 记两件事：**处理键 → 结果**（处理键 = 原片 sha256 +
处理参数，参数一变旧结果自然不再复用），以及每份内容的大小与最近使用时间。

- **复用**：上传落盘时顺带算原片 sha256，命中处理键且内容还在就直接链接成设备文件，立即就绪；
- **在用**：某台设备目录里有同样 sha256 的文件。删除文件/设备只删链接，内容变成"缓存中"；
- **淘汰**：总大小超过配额（默认 16GB，后台可改）时按最近使用时间清掉未在用的内容，在用的永不清。
  上传/处理完成、删除、改配额后立即整理，平时每小时一次，顺带纳入直接拷进目录的文件。
  配额不能低于在用总量；在用已占满配额时拒收新上传。

设备端对缓存区一无所知。

## 5. 装机、自注册、整包 OTA、通信安全、现场救援

操作步骤见 [deployment.md](deployment.md)，设计要点：

- **一键装机**：设备刷公版 Armbian，以 root 执行 `curl -fsSL http://<服务器>:9000/install.sh | ENROLL_TOKEN=… sh`。
  脚本由服务端生成（填好 HTTPS 地址、证书指纹与证书，不含口令），凭注册口令下载最新上传的设备端程序包，
  执行包内 `install-agent.sh`：写 `agent.json`、按 OTA 布局安装（含依赖）、HDMI/CMA 启动参数、enable 服务、重启。
  系统层面的设置全部由程序包里的脚本负责，不做定制系统镜像。批量时 `make-image.sh` 往公版 Armbian 镜像里加一个
  首次开机服务（设 root 密码、跳过 Armbian 首次登录向导、执行一键装机），插卡上电即自动装机；
- **离线依赖包**：GStreamer 等依赖若每台都从境外 apt 源下载，装一台要十几分钟、还离不开外网。`make deps` 在 armhf 容器里
  用空的 dpkg 状态让 apt 下载**完整依赖闭包**（含 libc 等基础库，设备镜像比打包时旧也装得上）并生成平铺 apt 索引；
  后台上传后，设备的 `deps.sh` 临时只用 `https://<服务器>:9001/apt/<代号>/` 这一个源安装，apt 只信任服务端证书
  （与代理固定的是同一张），局域网几秒下完。`update.sh` 每次都调用它，所以**新版本新增的软件包随 OTA 装上**，
  装不上就不切换。依赖包按 Debian 版本代号区分，对不上或安装失败时退回在线 apt；它一两百 MB，所以单独上传，不进 OTA 程序包；
- **编号与自注册**：编号取主机名（非公版默认值时），否则 SoC 序列号后 8 位（`opi-xxxxxxxx`），再退回 MAC；
  密钥首启随机生成并持久化，凭 `enroll_token` 自注册，后台立即可见。同 ID 不同密钥的注册被拒（409），
  记为"待确认"，运营方核对后可在后台接受新密钥（设备丢了身份文件时用，配置全部保留）——不自动接受，
  因为 `enroll_token` 在每台设备上都有；
- **整包 OTA**：OTA 包就是装机用的程序包（`VERSION`、`display-agent`、`update.sh`、回滚与自检脚本、systemd 单元），
  随程序一起变的系统调整也能 OTA。后台上传（服务端从包内读版本并校验）→ 立即/定时下发（定时由服务端判定）→
  清单 `update` → 设备下载、校验、解到 `versions/<版本>/`、以 root 执行包内 `update.sh` →
  成功才原子切换 `current`/`previous` 符号链接、退出由 systemd 拉起 → 首个心跳成功即确认。
  `update.sh` 失败不切换，原因随心跳的 `update_error` 上报，5 分钟后重试（与清单是否变化无关）；
  `rollback-check.sh`（ExecStartPre，装在固定路径）在新版本连续 3 次启动未确认后把 `current` 切回 `previous`。
  约定 `update.sh` 幂等、软件包只经 `deps.sh` 安装、版本目录以外的改动向前兼容（回滚不撤销它们）；
- **通信安全**：主端口（默认 9001）是 HTTPS，服务端首启在 `data_dir/tls/` 生成长期有效的自签证书；
  设备固定证书公钥（SPKI）的 sha256 指纹，不校验有效期与主机名——与设备时钟、服务器 IP 无关。
  HTTP 端口（默认 9000）只提供装机脚本与程序包（凭注册口令），其余 301 到 HTTPS。
  设备请求另有 HMAC 签名（时间戳 ± 5 分钟、常量时间比较）。程序包不另做签名：服务端被攻破时整个系统都不可信，
  这一层签名增加的保护有限。剩余风险见 deployment.md 第 8 节；
- **设备访问凭据**：插卡即装镜像让所有设备 root 密码相同，而 Armbian 默认允许 root 密码 SSH——泄露即全网可登录。
  所以 root 密码（服务端只存 SHA-512 crypt 哈希）与 SSH 公钥在后台统一设置、随清单下发（同样经指纹固定 + 签名，
  只有服务端能下发），代理用 `chpasswd -e` 写密码、整份写 authorized_keys，有公钥时加一份 sshd 配置只允许密钥登录。
  人员变动删公钥、密码泄露重设，一个轮询周期内全部设备跟上；不放进程序包，因为程序包是公开构建的；
- **系统不自行升级**：`update.sh` 关掉 apt 定时任务、锁定内核/dtb/u-boot（升级可能弄坏显示与硬解），系统层面的变化
  只随整包 OTA 有计划地发生；
- **现场救援**：设备连不上服务端而屏幕被播放画面占着时，插 USB 键盘按任意键：代理停掉播放进程、释放 DRM，
  tty1 控制台显示设备编号、IP、MAC、服务端地址与连接状态，可直接登录；键盘 15 分钟无操作自动恢复播放。
  设备在线时后台有 IP，直接 SSH，不需要远程启停进程。

**无外网运行**：设备按服务端响应的 `Date` 头签名，未被 NTP 同步时还把系统时钟校到服务端时间（设备没有 RTC）；
HTTPS 不校验有效期，时钟不准也能连；域名解析失败时退回上次实际连上的地址；开机不等网络、先播本地缓存；
服务端连不上时持续喂看门狗；控制请求短超时、大文件下载按停滞判定失败；设备端不走环境代理；服务端内嵌时区数据。
逐项说明见 deployment.md 第 9 节。

## 6. 可靠性

| 机制 | 覆盖的故障 | 状态 |
|---|---|---|
| systemd `WatchdogSec=90` + `Restart=always`：主循环健康才喂狗，等待重试、下载、执行 `update.sh` 期间也持续喂 | 代理假死、崩溃 | 已实现 |
| 播放进程守护：退出或 10 秒一次的状态查询不回就重启，并重新下发当前画面 | 播放进程崩溃、卡死 | 已实现 |
| 断网播缓存、原子切换、`current.json` 恢复、文件与身份落盘（fsync + rename） | 断网、断电 | 已实现 |
| OTA 失败不切换、连续 3 次启动失败自动回滚 | 坏程序包 | 已实现 |
| SoC 硬件看门狗（`/dev/watchdog`） | 内核 panic、系统整体假死 | 待做 |
| 只读根文件系统（overlayfs），媒体缓存放可写分区 | 断电损坏系统盘 | 待做 |
| 离线告警（微信/短信） | 运营方先于客户发现故障 | 待做 |

这些系统层面的设置都可以写进程序包的 `install-agent.sh`/`update.sh`，随包 OTA。

## 7. 技术栈与规划

- 服务端：Go 单二进制；状态存 JSON 文件；模板与测试卡用 `golang.org/x/image` 渲染；ffmpeg 转码、poppler 渲染 PDF；
- 管理后台：内嵌单页 HTML + 原生 JS（局域网工具，不引前端框架与构建链）；
- 设备端：Armbian + GStreamer（v4l2codecs 硬解 + DRM 图层直出，Python 播放进程）+ Go 代理。

设计取舍：保留设备轮询而不是 MQTT（ETag/304 让轮询成本近零，少一套要运维的组件；需要秒级推送时再引入）；
本地化部署而不是云存储（外网中断不影响分发与播放，小批量下也省云成本）。

**规划**（未实现）：

- **客户自助上传**：微信小程序上传图片/视频（`wx.uploadFile`）、查看审核状态；
- **审核工作流**：上传 → 处理 → 待审核 → 通过/驳回（附原因）→ 运营方绑定到显示屏发布。现有上传处理直接复用；
- **公网入口**：小程序要求已备案的 HTTPS 域名，需要固定公网 IP + 端口映射或内网穿透、ICP 备案域名与证书。
  这是整个系统唯一依赖外网的环节，只影响客户上传，不影响已发布内容的分发与播放；
- 第 6 节里的待做项。
