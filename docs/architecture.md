# 内容分布式显示系统 —— 架构设计

> 硬件已确认：**Orange Pi One**（选型依据见 [hardware.md](hardware.md)）；
> 显示屏分辨率：**1440×900**；部署与运维步骤见 [deployment.md](deployment.md)。
>
> 本文讲的是**为什么这么设计**；怎么装、怎么用看 deployment.md。

## 1. 背景与目标

- 客户在**微信小程序**中上传介绍自己公司的图片/视频；
- **运营方**审核确认内容无误后，将内容发布到该客户**专属的显示屏**（LCD 1440×900）上循环播放；
- 显示屏数量为**小批量**，与运营方服务器同处一个场地局域网；
- 设计目标：低成本、可离线（外网中断不影响播放与分发）、无人值守可靠运行（防假死）。

## 2. 总体架构

服务端、媒体存储、转码**全部部署在运营方本地服务器**上，与显示屏同在场地局域网。
微信小程序经公网入口访问本地服务端；显示屏走局域网下载。
**外网中断只影响客户上传新内容，不影响已审核内容的分发与播放。**

```
                    公网                          场地局域网
微信小程序(客户) ──HTTPS──> ┌─────────运营方本地服务器─────────┐
   · 上传图片/视频          │  服务端 API                      │
   · 查看审核状态           │   · 审核工作流 / 内容状态机       │ <──轮询 manifest── 显示屏 1
                           │   · 设备管理 / manifest 生成      │ <──心跳上报──────  显示屏 2
运营方管理后台(Web) ──────> │  FFmpeg 本地转码                 │ ──媒体文件下载──>   ...
   · 审核 / 绑定 / 编排     │  媒体存储(本地磁盘 + Nginx 静态)  │                    显示屏 N
   · 设备监控 / 告警        │  元数据库(MySQL/SQLite)          │
                           └─────────────────────────────────┘
```

### 2.1 组成部分与职责

| 组件 | 职责 |
|---|---|
| 微信小程序（客户端） | 微信登录；上传图片/视频；提交审核；查看审核状态与驳回原因 |
| 运营方管理后台（Web，局域网访问） | 审核队列（通过/驳回+原因）；**内容与客户/显示屏的绑定由运营方指定**（客户不参与绑定）；播放列表编排；设备监控（在线/版本/告警） |
| 服务端（RESTful API） | 内容状态机；设备管理（注册/绑定/心跳）；按设备生成带版本号的播放清单 manifest；调用本地 FFmpeg 转码 |
| 存储与转码（本地） | 媒体文件存本地磁盘，由 Nginx 静态分发（可选 MinIO）；FFmpeg 统一转码；元数据 MySQL/SQLite；定期备份（可选云端异地备份） |
| 显示屏设备（边缘端） | 局域网轮询 → 下载缓存 → 循环播放；多级看门狗；状态上报 |

### 2.2 前置条件：小程序公网入口

微信小程序的网络请求要求服务端具备**已备案的 HTTPS 域名**。本地化部署下需要：

- 固定公网 IP + 端口映射，或 frp/nps 等内网穿透到一台有公网 IP 的跳板；
- 一个已 ICP 备案的域名 + HTTPS 证书（Let's Encrypt 即可）；
- 在小程序后台配置该域名为"request/uploadFile 合法域名"。

这是整个系统**唯一依赖外网**的环节。

## 3. 内容生命周期（状态机）

```
客户上传 ──> 待转码 ──FFmpeg──> 待审核 ──运营方通过──> 已通过 ──绑定/编排──> 已发布(进入设备manifest)
                                  │
                                  └──运营方驳回(附原因)──> 已驳回(客户可见原因，可重新上传)
```

- **统一转码**是关键环节：所有上传视频经 FFmpeg 转码为 **H.264 / MP4（faststart），缩放至 1440×900 内接（保持比例、必要时留黑边）**，图片同样缩放至 1440×900 内接。这保证了低价 SoC 上解码 100% 可用，避免客户上传的奇异编码（H.265 10bit、VP9、竖屏 4K 等）在端侧播不动或花屏。
- 转码完成后计算 sha256 与文件大小，写入元数据，供端侧校验。

> **当前实现**：运营方在管理后台上传时即转码（见 5.2.1）。最初设想运营方素材可控、只做校验即可，
> 现场证明不行——即使编码是 H.264，原片 10~20Mbps 的码率也会让 H3 持续发热、降频乃至过热关机。
> 与上面的设想有一处不同：缩放是**等比缩小到 1440×900 以内、不留黑边**，铺满由设备端的 cover 完成。

## 4. 分发协议（轮询方案细化）

保留"设备轮询"的原设想（实现简单、故障模式清晰、无长连接状态要维护），用 HTTP 条件请求把轮询成本降到极低：

### 4.1 拉取播放清单

```
GET /api/v1/device/manifest
Headers:
  X-Device-Id:   <设备ID>
  X-Timestamp:   <unix 秒>
  X-Device-Sign: <HMAC-SHA256(device_secret, timestamp + method + path)>
  If-None-Match: "<当前已应用的清单版本号>"
```

- 无更新 → `304 Not Modified`（响应体为空，开销极小，局域网可设 5~10s 轮询）；
- 有更新 → `200` + JSON：

```json
{
  "version": "3f9c1a2b7d04",
  "items": [
    { "type": "video", "name": "promo.mp4", "url": "/media/scr-0017/promo.mp4",
      "sha256": "…", "size": 1937024, "duration": 0 },
    { "type": "image", "name": "menu.jpg", "url": "/media/scr-0017/menu.jpg",
      "sha256": "…", "size": 186000, "duration": 10 }
  ],
  "layout": {
    "canvas_w": 1440, "canvas_h": 900,
    "media": { "x": 720, "y": 0, "w": 720, "h": 900 },
    "overlay": { "type": "image", "name": "ovl_a1a2b9def825.png",
                 "url": "/render/scr-0017/ovl_a1a2b9def825.png", "sha256": "…", "size": 6046, "duration": 0 }
  },
  "commands": []
}
```

- `version` 是条目、指令、叠加布局的哈希：任何一项变化都会变，内容不变则稳定；
- `items` 是媒体区按顺序循环播放的内容；`duration` 只对图片有效（来自模板），视频播完即切；
- `layout` 只在模板有媒体区且媒体区有内容时出现（见 5.2）；没有时 `items` 是一张整屏渲染图；
- 文件由同一个服务进程用 `http.ServeFile` 分发（支持 Range 断点续传），同样要求设备签名、
  且只能取自己目录下的文件。几十台设备的规模下不值得再引一个 Nginx；
- `commands` 目前只有 `update`（程序 OTA，见第 6 节），随轮询顺带下发，无需长连接。

### 4.2 设备端更新流程

1. 收到新 manifest → 对比本地缓存，只下载缺失/变更的文件；
2. 下载支持**断点续传**（HTTP Range），完成后校验 **sha256**；
3. 所有条目就绪后**原子切换**播放列表（当前立即切换；"播完当前项再切"留待后续）；
4. 删除不再被任何 manifest 引用的旧文件；
5. 任一环节失败 → 保持旧列表继续播放，指数退避重试。

**断网兜底**：设备始终播放本地已缓存内容；网络恢复后自动追平最新版本。

### 4.3 心跳与监控

```
POST /api/v1/device/heartbeat
Body: { "agent_version": "1.0.3", "ip": "192.168.1.50", "uptime": 86400, "disk_free_mb": 2048,
        "temp_c": 52, "hwdec": "no", "output_w": 1440, "output_h": 900,
        "poll_interval_s": 10 }
```

注册与心跳的报文类型定义在 `internal/manifest/protocol.go`，两端共用。
设备正在显示哪个版本不在心跳里：每次轮询的 `If-None-Match` 已经带着了。

- **在线判断不靠心跳**：设备的任何签名请求（轮询、心跳、下载文件）都算联系过，约 3 个轮询周期
  （默认 30 秒）没有任何请求即判离线。只看心跳的话阈值压不下来（漏一次心跳就会误判），
  而轮询本来就每 10 秒一次；下载也要算，因为设备下载大文件时轮询会暂停；
- **轮询与心跳间隔由服务端规定**（`server.json`），随每个响应头 `X-Poll-Interval` / `X-Heartbeat-Interval`
  下发（含 304 与注册响应），设备照办；服务端据此算离线阈值；
- 心跳默认 1 分钟一次，只承担健康上报（温度、硬解、输出分辨率、运行时长、剩余空间）与 OTA 确认；
- 离线告警（微信/短信通知）尚未实现。

## 5. 管理后台、设备属性与显示模板（M1 增补，已实现）

### 5.1 管理后台 Web UI

服务端内嵌单页管理后台（`GET /admin`，X-Admin-Token 认证；写接口在未配置 token 时一律拒绝）：

- 设备列表：在线/离线状态、**离线显示最后在线时间**、当前版本、硬解/温度/输出分辨率/运行时长，
  以及内容同步状态（等待刷新 / 正在刷新 / 已显示最新内容）；
- 每台设备：**测试屏**下发（1/5/15 分钟/取消）、**key-value 属性**编辑（如 `room=302`）、
  **内容**（模板选择 / 左右对调 / 播放列表：选中即入列、逐个上传带进度、上传与转码中即可拖动排序，
  排序用 Pointer Events 实现，鼠标与 iOS/iPadOS 触屏同一套代码，顺序自动保存）；
- 模板管理（仅运营方）：表单编辑、JSON 高级编辑、服务端渲染预览。首次启动自动播种一个可用的
  左右分屏模板并设为全局默认；最后一个模板不可删，删掉全局模板时全局自动改指向剩下的模板。

**同步状态怎么来的**：服务端把决定一台设备清单的全部输入（测试屏、生效的模板及其内容、属性、
左右对调、播放列表文件的名字/大小/修改时间、待执行的更新指令）汇总成一份 `content`
（只读状态和文件元数据，不渲染），清单只由它生成，后台只看它的指纹——两边用的是同一份数据，
指纹天然覆盖清单的全部输入。设备每次轮询时记下"当时的指纹、算出的版本、设备带来的
`If-None-Match`（它正在显示的版本）"。后台刷新时重算指纹：和上次不同 → 等待刷新（它该显示的内容变了，
它还没来取）；设备显示的版本 ≠ 应显示的版本 → 正在刷新（在下载）；一致 → 已显示最新内容。
只看这台设备自己的输入，改别的设备不会让它闪一下"等待刷新"；时段计划到点切换、测试屏到期这类
没有任何写入的变化也能及时体现。不需要设备额外上报，复用现有的 ETag 轮询。
另有测试逐项核对"清单版本变了 ⇒ 指纹也变"。

### 5.2 核心机制：模板在服务端渲染成图

模板模型：画布 + 区域列表。区域类型：

| 类型 | 内容 | 谁来画 |
|---|---|---|
| `attribute` | 设备属性值（按 key 取，如 `room`） | 服务端 |
| `text` | 固定文字 | 服务端 |
| `media` | 该设备的播放列表：图片/视频 | **设备端**（每个模板至多一个） |

服务端把模板合成为一张 1440×900 PNG（纯 Go，`golang.org/x/image`）。有两种产物，取决于
媒体区里有没有内容：

**A. 整屏图**（没有媒体区，或媒体区还没放内容）——整块渲染成一张图，作为普通图片条目走既有
manifest→下载→播放管线。设备端零改动，也是"刚建好还没传内容"时不黑屏的兜底。

**B. 叠加图 + 设备端播放**（媒体区有内容）——媒体区挖成全透明，清单里的条目就是媒体文件本身，
叠加图随清单的 `layout` 字段下发（画布尺寸、媒体区矩形、叠加图的 URL/sha256）。

设备端由 GStreamer 出画面（`internal/player/gstplayer.py`，Python 播放进程，随代理分发、由代理守护），
**不经 GPU、不做软件合成**，直接用显示控制器（Allwinner DE2）的两个硬件图层叠出整屏：

| 图层 | 内容 | 怎么来 |
|---|---|---|
| 上层（主图层，ARGB） | 模板叠加图，媒体区是全透明的"洞" | 播放进程经 libdrm 直接驱动：自己设显示模式，两块哑缓冲轮换，画好后台那块用 `drmModeSetPlane` 切过去 |
| 下层（VI 图层，NV12，硬件缩放） | 当前播放项，按 cover 撑满媒体区 | 每项一条 `playbin`，输出交给只管这一个图层的 `kmssink`。视频走 `v4l2slh264dec`（cedrus 硬解），NV12 dmabuf 零拷贝显示，`videocrop` 只打裁剪标记、`kmssink` 按标记取源矩形；图片在软件里裁剪、缩放成正好媒体区大小，1:1 显示 |

上层不用第二个 `kmssink`，是因为两个 `kmssink` 共用一个 DRM fd（只能有一个 DRM master）时会互相
干扰：各自等翻页/vblank 事件会抢走对方的事件，非阻塞翻页还会撞上另一边进行中的提交（EBUSY），
表现为画面卡住不动、也不报错。现在两个图层的提交都是阻塞式的（下一个 vblank 生效后返回），
谁都不向 DRM 要事件。图层 id 由播放进程经 libdrm 查出（主图层在上，第一个能显示 NV12 的覆盖图层在下），
上下顺序用 `zpos` 显式指定。这与 Kodi/LibreELEC 在 Allwinner 主线内核上的做法一致：
界面在主图层、视频在下面的图层、靠透明洞透出来。

视频输出方式按 `裁剪标记 → 不裁（留黑边）→ 再加软件转格式` 的顺序尝试，第一个真正放起来的就一直用
（播放进程重启后重新尝试）；每次退一步都在日志里写明原因。GStreamer 自身的错误和 `kmssink`、
`v4l2codecs` 的警告也转进日志（`GST_DEBUG`），现场排查不用另开调试。

叠加图按**显示屏实际输出分辨率**光栅化成预乘 alpha 的 BGRA（`<png>.1920x1080.bgra`），媒体区也按同一
比例换算：显示屏若按 1920×1080 输出而模板是 1440×900，画面整体等比放大，不会错位。输出分辨率由
`agent.json` 的 `display_mode` 决定（显示屏不提供时退回首选模式），播放进程据此设置显示模式。

**切换过渡**：约 0.6 秒"淡出到黑 → 淡入"，做在上层：往洞里填透明度渐变的黑色、逐帧切给主图层。
下层的硬解视频帧是 dmabuf，CPU 碰不得；上层每一步只重画洞所在的那些行。切换空档里洞是全黑的，
拆旧管线、建新管线的那一下看不出来；模板属性区始终不动。

模板合成不需要碰视频数据：属性文字变化只重发那张叠加图，视频原封不动。播放进程退出或卡死
（ping 不回）由代理重启，并重新下发当前画面。（视频本身仍会在上传时转码一次，原因见 5.2.1。）

> 本地用真实 GStreamer 验证了排期、坏文件跳过、解码器上报、cover 裁剪计算与图片裁剪缩放
> （fakesink 代替 kmssink、软解代替 cedrus），上层画面的拼法有单测。**DRM 图层叠加（zpos 与透明洞）、cedrus 硬解与 dmabuf
> 零拷贝必须在样机上确认**，再对整批设备下发。

其余不变：测试卡仍是整屏渲染图，走真实内容管线，本身就是对整条链路的现场验证；属性/模板/
播放列表一变 → 清单版本变化 → 设备在一个轮询周期内自动更新（服务端 `poll_interval_s`，默认 10s）。

设备清单生成优先级：**测试屏（未过期） > 模板**；测试屏到期后自动回落，无需清理任务。
总有一个模板可用：首启播种默认模板，最后一个模板不可删，所以不存在"没有模板"的分支。

**播放顺序只有一个来源**：后台上传/拖拽排序写入的顺序，加上直接拷进 `media_root/<设备>/`
但没记录过的文件（按名字排在后面）。后台列表与设备清单用同一个函数计算，看到的就是在放的。

**左右对调**：每台设备有一个 `mirror` 开关，渲染时把每个区域的 x 换成 `W-(x+w)`（文字本身不镜像）。
"属性在左"和"属性在右"两种设备用同一个全局模板即可，不必建两个。

注意：文字渲染需要 CJK 字体——服务端配置 `font_path`（如 `apt install fonts-noto-cjk` 后指向
NotoSansCJK），未配置时退回内嵌拉丁字体，中文会显示为方框。

### 5.2.1 上传转码

**视频**一律在服务端转码（`internal/transcode`，调用 ffmpeg）：H.264 High@4.0、x264 `fastdecode`
（关掉 CABAC 与环路滤波，解码 CPU 省三四成，文件大 10~20%）、等比缩到 1440×900 以内（只缩不放）、
≤ 30fps、码率约 2.5Mbps（上限 4Mbps）、去音轨、faststart。

设备用 H3 的硬件解码器（cedrus）放视频。它是无状态解码器，需要 V4L2 Request API：FFmpeg 上游
至今没有合入这部分支持（所以 mpv 只能软解，这是改用 GStreamer 的原因），GStreamer 的 v4l2codecs
插件（gst-plugins-bad，Debian 自带）则原生支持。持续高码率即使硬解也会发热，所以码率仍要压住。
`fastdecode` 是给硬解失效时兜底的：退化成软解（后台标红）也还放得动。
仍用 H.264 而不是 H.265：H3 上 H.264 硬解比 H.265 成熟，H3 不支持 10-bit HEVC，
局域网分发下省那点体积意义不大，服务端编码 H.265 还要慢 5~10 倍。
转码在后台串行执行（一段几百 MB 的原片可能要几分钟，同步做会让上传超时），产物先写成
隐藏文件、完成后改名，未完成前不会出现在清单里。H.265/VP9 等原片也照收，反正会被转成 H.264。

**图片**纯 Go 等比缩到 1440×900 以内：设备只有 1GB 内存，解码后的位图是 宽×高×4 字节。

**ffmpeg 只在服务端启动时检测一次**：装好或改了 `ffmpeg_path` 后重启服务端生效。

**没有 ffmpeg 时**不收视频（图片照常）。早期曾退化为"只校验编码、原样下发"，但码率控制不住，
等于把过热问题留到现场，所以删掉了这条退化路径；后台会醒目提示安装 ffmpeg。

**设备侧可观测性**：心跳上报实际用的视频解码器（硬解元素名，退化成软解时为 `no`）、
实际输出分辨率与 SoC 温度，后台设备列表里软解与高温标红、分辨率不对标黄，现场不用登录设备就能发现问题。

### 5.3 全局模板与时段计划

- **全局默认模板**：运营方设置一个模板，所有设备使用；每台设备只需在"内容"里上传自己的播放列表；
- **时段计划**：全局的 `{模板, 星期, 开始, 结束}` 列表，按顺序取第一条命中，支持跨午夜；无命中回落全局默认模板。
  服务端按本地时间（可配 `timezone`）在生成清单时解析，边界时刻渲染图变化 → 版本号变化 → 设备轮询内切换，**设备端零改动**；
- 清单解析优先级：**测试屏 > 设备专属模板 > 时段命中 > 全局默认**。

## 6. 批量部署：唯一编号、自注册、程序 OTA、安全基线（已实现）

操作步骤见 [deployment.md](deployment.md)，设计要点：

- **同一母镜像**烧所有设备；编号优先级：显式配置 > 主机名（Armbian Imager 自定义 hostname）> SoC 序列号后 8 位（`opi-xxxxxxxx`）；
  密钥首启随机生成并持久化，凭母镜像内的 `enroll_token` 向服务端 `POST /api/v1/device/register` 自注册，后台立即可见并随心跳在线；
  同 ID 不同密钥的注册被拒（409），防冒名；该请求记为"待确认"，运营方核对后可在后台接受新密钥
  （设备丢了身份文件时用，配置全部保留），不自动接受——`enroll_token` 烧在每台设备里，自动接受等于谁都能冒充；
- **程序 OTA**（更新的是代理二进制，不是 OS）：后台上传版本 → 立即/定时下发（定时由服务端判定，设备无需可信时钟）→
  清单 `commands` 携带 `update{version,url,sha256,size}` → 设备断点续传下载、校验、`current` 符号链接原子切换、退出由 systemd 拉起 →
  首个心跳成功确认；`rollback-check.sh`（ExecStartPre）在新版本连续 3 次启动失败后自动回滚到 `previous`；
- **安全基线**（`deploy/agent/harden.sh`）：关闭系统自动更新并锁定内核包；nftables 入站默认拒绝；
  **SSH 保留但仅密钥 + 仅运维地址**——设备难以物理触达，SSH 是 OTA 之外唯一的远程救援通道。

### 6.1 无外网运行

安装完成后系统只依赖局域网（运维细节见 deployment.md 第 9 节）：
设备按服务端响应的 `Date` 头校准签名时间（设备没有 RTC、连不上 NTP 也能认证）；
服务端域名解析失败时退回上次成功的地址；设备开机不等网络、先播本地缓存；服务端连不上时持续喂看门狗、
不会因为重试等待被 systemd 重启；控制请求短超时、大文件下载按停滞判定失败；设备端不走环境代理；
服务端内嵌时区数据。服务器时钟是时段计划的唯一时间基准，后台在它与浏览器时间相差较大时提示。

## 7. 设备端可靠性设计（多级看门狗）

单靠应用层 watchdog 不足以覆盖所有假死场景，采用四层递进：

| 层级 | 机制 | 覆盖的故障 |
|---|---|---|
| 1. 硬件看门狗 | SoC 内置 watchdog（`/dev/watchdog`，晶晨/全志/瑞芯微均支持），由喂狗守护进程喂狗 | 内核 panic、系统整体假死 → 硬复位 |
| 2. 进程守护 | systemd `Restart=always` + `WatchdogSec`（播放器需周期性 `sd_notify`） | 播放器崩溃、进程假死 |
| 3. 应用自检 | 播放器周期写心跳文件/上报播放进度；守护脚本检测"进度长时间不前进"则重启播放器 | 播放卡死但进程未死（如解码器挂起） |
| 4. 定时重启 | 每日凌晨业务空窗期定时重启（cron/systemd timer） | 内存泄漏、资源慢性耗尽等一切慢性病（保底） |

其他可靠性措施：

- **只读根文件系统**（overlayfs），媒体缓存放独立可写分区——断电不会损坏系统盘；
- 二手盒子方案自带 **eMMC**，天然比 SD 卡抗掉盘；开发板方案建议用工业级 SD 卡或 eMMC 模块；
- 设备身份首启自生成（编号取主机名或 SoC 序列号，密钥随机），凭 `enroll_token` 自注册，见第 6 节；
- 代理程序支持 **OTA**：manifest 的 `commands` 下发新版本 URL + 校验和，`current`/`previous` 符号链接切换，
  连续 3 次启动未确认自动回滚。

## 8. 对原设想的改进点汇总

| 原设想 | 改进 | 理由 |
|---|---|---|
| 设备轮询 server | **保留**，加 `If-None-Match`/304 条件请求 | 轮询成本降到近零，30s 级轮询也无压力；比 MQTT 少一套要运维的组件。量大或需秒级推送时再引入 MQTT 不迟 |
| 服务端接收/下发内容 | 清单只含元数据；文件由同一服务进程 `ServeFile` 分发（Range 续传、签名鉴权） | 几十台设备的规模不值得多运维一个 Nginx |
| （未提及） | 增加**统一转码**环节（上传时，H.264 / ≤1440×900 / ≤4Mbps） | 低价 SoC 硬解稳定性与发热的成败关键 |
| 端侧 watchdog | 扩展为**四级看门狗** | 单层 watchdog 覆盖不了内核假死/慢性泄漏 |
| （未提及） | 心跳 + 离线告警 + 远程指令 + OTA | 屏挂在客户面前，运营方必须先于客户发现故障 |
| 云端存储（常见做法） | **本地化部署** | 按需求：外网中断不影响分发与播放；小批量下也省了云成本 |

## 9. 技术栈与里程碑

**已采用的技术栈**：

- 服务端：Go（单二进制、零运行时依赖）；状态存 JSON 文件（规模小，省掉数据库运维）；
  模板与测试卡用 `golang.org/x/image` 服务端渲染；
- 管理后台：内嵌单页 HTML + 原生 JS（局域网工具，不引前端框架与构建链）；
- 设备端：Armbian + GStreamer（v4l2codecs 硬解 + kmssink 直出，Python 播放进程）+ Go 轻量代理（注册、轮询、下载、喂狗、心跳、OTA）；
- 转码：服务端调用 FFmpeg，后台串行队列，统一归一为 H.264 / ≤1440×900 / ≤4Mbps；
- 小程序（M3 待做）：微信原生框架，`wx.uploadFile` 分片上传大视频。

**里程碑**：

1. ✅ **M1 端到端打通**：服务端 manifest/心跳 API + 设备播放代理，ETag/304 轮询、
   断点续传、sha256 校验、原子切换、断网播缓存、systemd 软看门狗；
2. ✅ **M1 增补**：管理后台（在线状态/测试屏/设备属性/全局模板/时段计划）、服务端渲染模板、
   模板媒体区（视频/图片叠加合成）、上传转码、设备唯一编号与自注册、程序 OTA（失败自动回滚）、安全加固脚本；
3. M2 内容工作流：客户内容审核队列（转码已在 M1 完成）；
4. M3 小程序：上传 + 审核状态查询（含公网入口与域名备案）；
5. M4 可靠性收尾：硬件看门狗（`/dev/watchdog`）、只读根文件系统、离线告警。
